### Required product flow

1. Onboarding opens with one welcoming companion. Ask the user's name, goal and intended use, offering short suggestions and free text. Show an example customizable companion identity. For app development, explain briefly that Vercel/Supabase connection is a later step. Save the answers and companion, then enter home. Onboarding is not an account or integration setup.
2. Home shows large companions. Open or create a companion, rename it and choose its appearance. Each companion owns multiple missions. Creating a new companion provides an honest empty workspace rather than copying another companion's history.
3. A companion workspace combines general chat, a visible mission list and a clear create action. Mission creation offers app, research, monitoring and custom-goal examples. Require a short objective; offer an optional editable recommended date. A date is display data, not a real schedule.
4. An integrated mission detail shows goal, status, its own chat, progress and deliverables. Pause, resume and explicit goal edit remain visible where relevant. Stages/subtasks are secondary. General chat never changes a mission objective implicitly.
5. Exactly three initial mission seeds illustrate `active`, `waiting_permission` and `awaiting_review`. The review seed displays **Paused · Ready for review** because it does not run while awaiting confirmation; it is not a fourth paused seed. Ordinary `paused` behavior remains available through controls.
6. When simulated work considers the goal complete, its final deliverable enters `awaiting_review`; partial stage outputs can coexist with `active`. Confirming closes the mission; requesting corrections reopens the same mission ID and retains all history and deliverables. Reset demo affects only this application's data.

### Shared contracts for implementation

- Define typed `Profile`, `Companion`, `Mission`, `Message`, `ProgressEvent` and `Deliverable` models before dependent UI work. Use stable IDs and timestamps, never list indices as identity. `Companion` owns a general conversation; each `Mission` belongs to one companion and owns a separate conversation. Scope all reads and mutations to the selected IDs.
- Mission status is a discriminated union: `active`, `paused`, `waiting_permission`, `awaiting_review`, `completed`. A paused mission preserves its prior runnable/permission state. Review is non-running and completion is terminal until an explicit correction request.
- Allowed actions: active can pause or reach a demo permission/review checkpoint; waiting permission can approve or decline; approval resumes active work, decline pauses while retaining the unresolved gate. Resuming a paused permission mission returns to the permission decision, never silently approves it. Review offers confirm or request corrections, never generic resume. Confirm sets completed; corrections set active on the same ID and append the request. Completed missions cannot progress silently.
- Explicit goal edits preserve the mission ID, chats, events and deliverables and append an edit event. Editing cannot approve a pending permission or review implicitly. A permission decision concerns only the described simulated action.
- Centralize transitions in pure domain functions. Components call explicit actions through a small data interface. Put seed data and deterministic simulated responses/progress outside components. Use user-triggered demo advancement/checkpoints, without real network work, uncontrolled timers or claims of background execution. Pause, review and permission gates halt simulated advancement.
- Persist a versioned snapshot under a single named application localStorage key, with validation and a repository interface suitable for a future Supabase implementation. Handle unavailable/corrupt storage visibly and without crashing or overwriting unrelated keys. Missing data can initialize the demo; malformed existing data must not be silently treated as a successful load. Keep React state and persistence synchronized.
- Reset confirms the user's intention, removes only the owned key, restores first-run onboarding and seeds, and leaves unrelated origin data intact. No `localStorage.clear()`.
