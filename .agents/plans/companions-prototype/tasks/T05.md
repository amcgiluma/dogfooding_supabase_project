Import feature-owned `mission.css` with `mission-` prefixes and T02 CSS variables; no global/shared Chat styling. Show the actual mission state, not the mock's static scenario tabs. Display a discreet Demo caption; dates are targets, not real schedules. Use `Chat` from `src/features/chat/Chat.tsx`, keyed by mission/companion IDs with scope `{kind:'mission',companionId,missionId}`. This is the only mission chat rendered. No separate details page that hides the conversation.
3. Use `getMissionEvents`/`getMissionDeliverables` for chronological history/output, with stable keys and readable plain-text bodies. Progress is a demo stage value, never measured real work. Add a secondary “Stages and subtasks” disclosure with concrete static per-kind fixtures in `src/features/mission/stageFixtures.ts`: Shape, Prepare, Review, each with 1–2 short labeled subtasks fitting app/research/monitoring/custom. Derive simulated stage/subtask status from cursor/state: Shape complete at cursor>=1; Prepare complete at cursor>=3; Review ready at awaiting_review and complete at completed; otherwise pending. Show these as demo steps, separately from event history; do not add persistence entities. Correction cursor reset resets these derived statuses while previous artifacts remain visible. Distinguish older outputs by timestamp and never render arbitrary stored HTML.
4. Active offers Pause, explicit Edit goal and a clearly user-triggered demo advance action. Waiting_permission shows the exact action/resource/explanation with Approve/Decline; include Pause and Edit goal where appropriate. Pass the current gate.id to `decidePermission`; no blanket permission switch. Paused offers Resume and Edit goal; retained permission must return to the same decision after resume, with no implicit approval.
5. Awaiting_review offers Confirm complete or Request corrections plus explicit Edit goal. It has no generic Resume/advance. Completed shows closure and retains output/history; an explicit Request corrections may reopen it. Do not offer active work controls on completed. Submit corrections as a required trimmed reason; call `requestCorrections`, retain draft on error. It resets cursor/progress for a new correction cycle on the same ID and preserves messages/events/artifacts.
6. Edit goal uses a separately labeled form, requiring a trimmed objective and explicit commit through `editMissionGoal`. A chat message alone cannot edit it. Goal edits during permission/review retain those states/gates; completed must reopen through corrections first. All lifecycle controls await actions, prevent duplicate submission and surface ActionResult errors. Save failures already committed by T02 show the global memory warning; do not retry completed actions as failed writes.
7. Implement deterministic recipes through the existing `getDemoStep(mission)` and `getDemoReply(scope,text)` exports; do not change their signatures or action semantics. Fix cursor 0=progress, with a required partial deliverable for APP (optional for other kinds); 1=permission; 2=final review; >=3=null. Type returned fixtures using DemoStep, no casting or new dependencies. Each mission kind has short fitting copy and sample output: app proposal, research findings, monitoring update, custom note. Permission descriptions concern a specific simulated step, never a real integration.
8. `getDemoStep` returns null outside active so no recipe can bypass gates. `advanceDemo` consumes exactly one step centrally through T02. Progress steps may append partial outputs and remain active; review appends a final sample deliverable and enters awaiting_review. No timer, random response, network request or background execution. Correction cycles restart at cursor/progress 0, produce fresh IDs through T02 Runtime and keep prior results.

Partial outputs stay active; final output awaits confirmation. General chat remains unrelated. The secondary disclosure shows actual labeled stages/subtasks with cursor-derived demo status, including reset on corrections.
- Commands or inspections: Run actual T02 `pnpm typecheck`/`pnpm build`; inspect that UI calls shared actions rather than assigning status/cursor/objective. Verify cursor sequence with an injected runtime or integrated walk when available; no timers/network work.
