# Detailed plan: V01 — Focused lifecycle and persistence verification

- Type: Verification, Pending implementation dependencies. Option A and local verification are authorized.
- Goal and observable result: Automated checks prove consequential domain/persistence invariants with deterministic inputs and record reproducible results. Verification exposes defects; it does not patch product code.
- Dependencies and inputs: Completed T02/T05/T06 and implementation authorization; overview.md, T02 contracts, T05 recipes, T06 integration report and report template. Inspect actual exports before constructing tests.
- Scope: Own focused `tests/domain.test.mjs` and `tests/storage.test.mjs` and the V01 report. Coordinate one test-tooling addition with supervision after T06: use Node's test runner through `tsx`, with `test` script `tsx --test tests/*.test.mjs`, if no equivalent existing runner exists. No product-code edits or new UI tests. Preserve the application lockfile discipline.

## Execution steps

1. Inspect existing tooling and reports. Prefer an existing suitable runner; otherwise add only tsx as a dev dependency and test script, coordinated with root-file ownership. Tests may import TypeScript modules directly through tsx and use `node:test`/`node:assert/strict`; no React test framework or snapshot suite. Record Node/pnpm versions and exact commands.
2. Build a deterministic Runtime with fixed UTC timestamps and monotonic unique IDs plus a small in-memory fake implementing getItem/setItem/removeItem. Inject failures separately for read, write and removal. Do not touch browser data, live services or the user's real localStorage during pure tests.
3. Test onboarding once creates one profile/companion with exactly three coherent seed missions, unique linked IDs and correct active/waiting_permission/awaiting_review states. A second completeOnboarding fails unchanged. A newly created companion has no missions/history. Missing/wrong companion ownership fails unchanged.
4. Test conversations with two companions and two missions: user/demo replies append only in supplied scope, selectors separate all four conversations, and messages do not edit objectives or grant permission. Empty text and nonexistent scope fail unchanged.
5. Test active pause/resume and permission checkpoint: awaiting permission cannot advance; approval requires matching gate ID; decline yields paused with retained gate; resume restores the same pending gate; approval resumes active. Invalid/repeated decisions leave snapshot/history unchanged and neither approve nor deliver silently.
6. Test final delivery enters awaiting_review, halts advancement and references the appended deliverable. Confirm closes the mission; completed rejects advancement. A progress step with a partial output stays active. Edits while paused/permission/review preserve state/gate/ID/history and append an explicit edit event; completed rejects edits until correction.
7. Test corrections from review and completed reopen the same ID with cursor=0/progress=0, append the reason to mission chat/events and retain every earlier message/event/deliverable. Advancing the new cycle appends outputs rather than replacing old ones. Freeze/compare input snapshots to detect mutation; compare counts/IDs and behavior, not large snapshots of copy.
8. Test repository round-trip preserves full typed snapshot and links. Missing key returns empty. Malformed JSON, invalid discriminants/fields, dangling ownership/review references, duplicate IDs, bad dates/progress/cursor and unsupported schema report invalid/version outcomes rather than loaded/empty. Original raw value remains unchanged. Validate enough representative malformed examples to exercise boundary invariants, not every string field permutation.
9. Test unavailable read, denied/quota save and denied remove return explicit failures. Reset removes only STORAGE_KEY and preserves an unrelated sentinel. Verify no clear or migration behavior; invalid data is not implicitly written over. Provider serialized updates/save-failure retry semantics require browser evidence in V02 because this task deliberately avoids mounting React with another framework.
10. Run focused tests, typecheck and build once; repeat only after a reported correction. On failure report the minimal reproducible invariant/actual result to supervision, which assigns a correction task. Do not edit product files. Write `reports/V01.md` with changed test/tooling paths, commands/results, cases, failures and explicit coverage limits.

## Verification

- Main and edge cases: Permission gates, stopped progress, partial/final delivery, immutable same-ID correction, ownership/chat isolation, schema rejection and scoped reset are asserted with deterministic IDs/timestamps.
- Commands or inspections: `pnpm test`, `pnpm typecheck`, `pnpm build` or recorded T02 project-scoped equivalents. Inspect tests for meaningful outcome assertions, no arbitrary time sleeps or implementation-mirroring snapshots.
- Expected result: All focused tests/build checks pass, sentinel remains intact on reset, corrupt data survives rejected load, and report gives exact evidence. Provider/UI/browser behavior is not declared verified here.

## If the plan is insufficient

Return to supervision for changed exports, essential untestable invariants, unavailable tooling or any need to change product code. Add only focused cases needed for consequential behavior; do not broaden into endless smoke/regression checks or install a large testing stack.
