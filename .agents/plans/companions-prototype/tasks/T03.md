## Execution steps

1. Confirm T02's imports and use `useApp()` from `src/app/AppProvider.tsx`, returning `{snapshot,storage,actions,view,navigate}`. Use component-imported `src/features/onboarding/onboarding.css` and `src/features/home/home.css`, with `onboarding-` and `home-` class prefixes. Use T02 CSS variables; no global element selectors or shared `.screen`/`.field`/`.message` classes. T03 and T04 may execute independently without editing App/global CSS.
2. Build Option A's conversational onboarding with one companion: warm English welcome, user name, goal and intended use. Use the 1fr/.9fr text/art layout with large skull art; at 720px and below use one column with artwork first. Show real submitted answers as short conversation turns rather than the mock's hard-coded Juanma responses. Offer goal/use suggestions plus free text; preserve draft answers when going back. Keep customizable companion name/appearance in a secondary disclosure as approved. Allow `'skull' | 'wolf'`; the local example identity is not generated live. For app-development suggestions, explain briefly that Vercel/Supabase can be connected later. Show that this demo saves on the device, without collecting credentials or implying a real memory/connection.
3. Validate trimmed required fields and show a concise associated error without clearing entries. Submit through `await actions.completeOnboarding({name,goal,intendedUse,companionName,appearance})`. All actions return `ActionResult<T> = {ok:true,value:T} | {ok:false,error:{code,message}}`. Disable duplicate submission while pending. On success, call `navigate({kind:'home'})`; on failure, retain form data and show the returned error. Never create seeds in the component: T02 creates exactly one companion with exactly three seed missions.
4. Build home from `snapshot.companions`, keeping Option A's prominent character artwork and rule-separated name/actions; additional companions repeat the same simple layout without decorative cards. Use about 370px desktop/260px mobile artwork height, with responsive containment. Open using `navigate({kind:'workspace',companionId,missionId:null})`. Give create, rename and appearance controls accessible labels and clear focus. Create calls `actions.createCompanion({name,appearance})`; rename calls `actions.renameCompanion(id,name)`; appearance calls `actions.setCompanionAppearance(id,appearance)`. Consume returned errors. New companions receive no missions/history; do not copy another companion's data or seed missions again.
5. Support an empty companion list defensively with a clear create action. Use stable IDs as keys, preserve whitespace only where intentional, and render user text normally without HTML injection. Forms/dialogs must support keyboard submit, cancel, visible focus and focus return; associate errors using aria-describedby/aria-invalid and focus the failed field. Prefer native dialog if a modal is needed, or simple inline forms. Keep artwork responsive and main controls readable on narrow screens; no animated decoration.
6. Run T02's build/typecheck scripts and inspect action ownership/typing. Notify T06 of exports, required asset references and integration needs. If integrated App already exists and composition is owned by T06, exercise first-run save and create/rename/appearance without changing composition. Otherwise report runtime verification deferred to T06/V02, not falsely completed. Write `reports/T03.md` from the report template with changed files, checks and remaining integration evidence.
