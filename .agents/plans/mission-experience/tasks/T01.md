## Execution steps

1. Read the inputs and inspect the current Raiden reserved-art approach. Build on its identity: background `#000`, white primary text, accent `#67e8f9`, 1px separators `#30363c`, restrained secondary text `#b5bec8`. Use Rajdhani 600/700 for headings and stage numbers, IBM Plex Sans 400/500/600 for reading and controls. Load copied local fonts using `font-display:swap`; add a data favicon to avoid network noise. Use real black for product surfaces, no decorative cards/pills, no gray introductory subtitle above sections, no em dashes, no pulse/spinner/shimmer, blur or infinite animation. Main actions may have cyan fill with black text; secondary actions are plain bordered buttons or underlined text. Touch controls at least 44px high; body text 14–16px, visible cyan focus rings. Give headings, tables, and rows breathing room without making the product sparse.
2. Create the following complete alternative layouts. Give all three the same content, behavior and toolbar, but use different hierarchy and geometry, not only colors.
   - **A / `conversation.html`: Conversation + lateral brief.** Desktop product shell has compact 180px navigation, central chat, and Details dock when opened. Creation opens a single approximately 960px-wide native dialog: 2/3 width text conversation, 1/3 persistent brief separated by a vertical rule. Raiden's outlined geometric mount is about 96px beside the current prompt, name immediately beside the speech. Earlier short prompts and the user's answers remain visible as a compact transcript; only the current step has inputs. Brief shows Goal, Type, Target and updates as inputs change. Details dock uses a vertical three-stop route beside a chronological timeline and separated deliverables. Mobile creation collapses to conversation followed by the same brief, which remains in the dialog; Details uses a full-width native modal dialog.
   - **B / `focus.html`: One central question + route map.** A narrow 64px product rail leaves a broad canvas. Creation uses a single approximately 880px dialog with centered outlined 128px companion mount, 40–48px Rajdhani prompt, and one focused form group. A connected horizontal `01 → 02 → 03` route provides step orientation; the mission brief is a narrow ruled row below the form, not a sidebar. Details is a broad visual map with three horizontal stations, their subtasks immediately below, and history/results in two columns underneath. A single nonanimated rail shows overall demo progress. On mobile the map becomes three stacked stations connected vertically and history/results become a single column.
   - **C / `compact.html`: Conversation + bottom brief / instrument view.** Compact 156px mission list, dense workspace, shorter approximately 760px creation dialog. Raiden's outlined mount is about 56px beside a concise name and prompt. Previous answers are short transcript rows. A persistent full-width ruled brief below the current form uses a definition-list row, and navigation/actions sit beneath it. Details is a dense instrument panel: objective/status/date header, numeric demo estimate and thin progress line, three-stage ledger with subtasks, chronological event log, and results list. Use simple column rules and rows, never dashboard cards. Mobile moves brief fields and details columns into stacked rows without reducing readability.
   In every proposal the companion mount is an intentional cyan outline/bracket/diamond geometric reservation with `Raiden` as visible text, not a skull drawing, blob, photo, stock asset, or an image failure. Decorative geometry has `aria-hidden=true`; no “art coming soon” product copy is necessary.
3. Add a 44px or taller preview toolbar **outside the product shell**, with “Interactive mock · fictional demo”, link “Compare proposals” to `index.html`, and labelled native select “Preview state”. Its values are `creation`, `active`, `paused`, `permission`, `review`, `completed`. Initial value is `creation`, opening creation immediately. Choosing another value opens the corresponding sample mission with Details visible. Selecting `creation` returns to the existing creation draft without losing it. Switching sample states reloads a consistent fictional fixture and does not write persistence. The toolbar may wrap on small screens. Product header includes “Raiden”, “New mission”, and “Details”; do not add unimplemented navigation links or decorative button menus. Keep all product copy English (`lang=en`), comparison Spanish (`lang=es`).
4. Implement the same three-step creation controller inside one dialog/menu. Keep a single in-memory `draft = {objective,kind,targetDate}` and `step = 1|2|3`; no new mission fields. Initialize objective empty, type `app`, date empty. Suggested sample text is an optional explicitly labelled button “Use example” filling `Build a small project space`, never an automatic user answer.
   - Step 1: heading/prompt “What should we work toward?”; Raiden text “Tell me the result you want. We’ll shape the first step together.”; labelled “Mission objective” textarea, optional example button, and “Continue”. Require trimmed nonempty objective; whitespace-only attempts stay here with inline `role=alert` error and focus at the textarea. Do not simulate AI parsing or infer task data.
   - Step 2: “What kind of mission is this?”; Raiden text “Choose the work we’re starting. Add a target if it helps.”; native radio group labelled “Mission type” for `App`, `Research`, `Monitoring`, `Custom`; native date input labelled “Target date (optional)”. One concise explanation “A target, not a schedule.” beside the date. “Back” and “Review mission”. Date may be omitted or cleared; no recurrence, deadline enforcement, permissions, integration, or schedule fields. Preserve all values going backward.
   - Step 3: “Here’s our mission.”; Raiden text “Check the goal and details. Start when you’re ready.”; readable Goal / Type / Target summary, with “No target date” when empty. “Edit objective” goes directly to step 1, “Edit type and target” directly to step 2. Both preserve all fields. “Back” goes to step 2. Only “Start mission” creates the in-memory mission; close creation, open that mission workspace, make Details visible, status active, progress 0%, cursor 0, and one “Mission created.” history event. No fake task work or success toast detached from the mission.
   The dialog remains mounted/open during all step changes, with the same outer menu. Native `showModal()` manages focus containment. On each step change focus the first relevant field (review heading may use `tabindex=-1`). Close button and Escape retain the draft, close the dialog and return focus to “New mission”. Reopen restores current draft/step. Never nest creation and Details dialogs: close Details before opening creation, and close creation before showing mobile Details. Long dialogs scroll internally while every action remains reachable. Visible transcript text may paraphrase submitted answers, not fabricate assistant analysis.
5. Implement one small shared in-memory demo state machine in `demo.js`, with matching semantic DOM hooks on each page. Layout classes may differ, state rules may not. Keep rendering safely escaped/textContent so user-entered objective/corrections cannot inject HTML. Do not import app modules or call app APIs. All mission advancement is user-triggered; no timers advance work or generate results. A bounded prompt typewriter is the only permitted timed behavior (step 7). Maintain mission kind/objective/target, status, progress, cursor, optional gate, resume state, events and deliverables. Use deterministic fictional timestamps starting `2026-10-06T09:00:00Z`, incrementing one minute per event; sample target `2026-10-20`. Sample objective is `Build a small project space`, kind app. Mark progress “demo estimate” in text and `aria-label`; do not invent hours, confidence, work counts, individual subtask completion, or other metrics.

   | Preview / transition point | status | cursor | progress | Stages 1 / 2 / 3 | History and result consistency |
   | --- | --- | --- | --- | --- | --- |
   | Newly created mission | active | 0 | 0% | To do / To do / To do | Creation only; no deliverables |
   | Active preview, or first advance | active | 1 | 32% | Complete / To do / To do | Created, first progress; app only also has first-screen partial output |
   | Paused preview | paused, resume active | 1 | 32% | Complete / To do / To do | Active preview plus “Mission paused.” |
   | Permission preview / second advance | waiting_permission | 2 | 32% | Complete / To do / To do | Prior events + permission requested; partial app output retained |
   | Approved permission | active | 2 | 32% | Complete / To do / To do | Add permission approved; no final result yet |
   | Review preview / third advance | awaiting_review | 3 | 100% | Complete / Complete / Ready to review | Approval + final deliverable event; app partial plus final output |
   | Completed preview / confirmation | completed | 3 | 100% | Complete / Complete / Complete | Add completion confirmation; same output now confirmed |

   Rules are exactly those in `MissionDetail.stageState`: stage 1 complete when cursor ≥1, stage 2 complete when cursor ≥3, stage 3 ready only awaiting review and complete only completed. Do not equate 100% with confirmation. Display a stage state label and distinct check/open circle/review glyph plus connecting line; color alone cannot encode state. Subtasks remain plain source-derived lists, not invented individually checked items. All mission kinds get the exact fixture stage titles/subtasks from `stageFixtures.ts`; inline these fixtures unchanged. Use kind-dependent copy from `simulation.ts`: first progress summaries for each kind; first partial deliverable exists **only for app**, titled “First screen proposal” (kind app); final titles `Prototype handoff` / `Research findings` / `Monitoring update` / `Mission result` with kinds app/report/update/note. Bodies can be concise excerpts of current simulated briefs that plainly state no external work occurred. No searched sources, deployed app, active monitoring, external artifacts, or invented actual URLs. Stage diagrams illustrate existing fixture data, not executable subtasks.
6. Provide real controls for all visible mission actions and map them as follows; reuse one action renderer across proposal surfaces within each file.
   - Active: “Pause mission”; advancement label by cursor: 0 “Advance demo one step”, 1 “Advance to permission”, 2 “Prepare final review”. First advance sets 32%, cursor 1, exact kind summary, and app partial result; second sets unresolved gate/cursor 2 with no progress change; third sets 100%, cursor 3, awaiting_review, adds final output.
   - Permission: visible action/resource/explanation using the exact kind entries in `simulation.ts` (app: “Review sample project data” / “Example project information”; research: “Review sample research sources” / “Example source summaries”; monitoring: “Review a sample update” / “Example monitoring signal”; custom: “Review a sample external result” / “Example project information”). “Approve this action” returns active cursor 2 with gate resolved; “Decline” pauses while retaining that gate and a declined history event; “Pause” similarly retains the gate. Explanation says connected version would require permission, no service connected. Resume from those paused states returns to permission, never skips the gate.
   - Paused: show the reason and “Resume mission”; restore active or permission according to resume state without changing percentage/stage/history. No advance button while paused.
   - Awaiting review: status “Paused · Ready for review”, “View deliverable” opens Details and focuses the results heading; “Confirm complete” sets completed and appends confirmation; “Request corrections” opens labelled textarea with Send/Cancel, empty submissions prevented, Escape cancels and restores trigger focus.
   - Completed: show confirmation and keep history/results; “View deliverable”, “Request corrections”. Corrections from review or completed reset mission active/cursor 0/progress 0, keep objective/type/target **and retain earlier events and deliverables**, add correction text as a new event. Earlier final output then reads “earlier output”, not “ready for review”. No direct goal edit while completed. Do not duplicate current final output when toggling preview states.
   - Details: heading/objective, type/status/optional formatted target, progress, stage/subtask diagram, chronological history with `<time>`, and deliverables with title, kind, timestamp, body and state label. Empty history/output messages for fresh missions. “Edit goal” available outside completed: inline textarea Save/Cancel, trimmed validation, changes objective and adds goal-edited event; no new field. “Close details” works; header “Details” reopens. On desktop Details is a panel; on mobile native dialog with Escape/Close and focus restored to its opener. “View deliverable” scrolls/focuses the deliverables heading even if already open. Keep creation and Details focus logic explicit.
7. Implement responsive layout from 1440px down to 390px, with an intermediate switch around 840px. Set `min-width:0`, break long objective text, and allow vertical scrolling; no page horizontal overflow. Hide or simplify unneeded navigation columns on mobile rather than adding a hamburger submenu. Avoid fixed page heights that cut off forms. Progress track has `role=progressbar`, min/max 0/100 and current value. Use `<form>`, `<fieldset>/<legend>`, proper labels, native buttons/select/date, semantic ordered lists and headings. Error text references the field via `aria-describedby` / `aria-invalid`. Inputs/radios react to keyboard; Enter submits the current form, textarea newline stays newline. No hover-only information. Make DOM reading order match mobile layout. Add one finite prompt typewriter per step transition, completing within approximately 800ms: full accessible prompt is available immediately, visible typed copy is aria-hidden, and inputs/actions are never blocked by typing. Reduced-motion users see the complete prompt immediately. Cancel pending typing on step changes/dialog close; pause on document hidden and resume when visible, with no polling loop. Add a stable hook such as `data-typewriter` to the visible copy so V01 can inspect it. Other transitions are short opacity/transform only and disabled by reduced motion. No infinite animations, animated cursor or repeated background effects anywhere.
