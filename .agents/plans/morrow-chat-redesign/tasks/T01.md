# Detailed plan: T01 — Three static chat proposals and chooser

- Type: implementation
- Goal and observable result: create a polished Spanish chooser and three meaningfully different English UI proposals. Each proposal exposes onboarding, populated chat, permission, and review states without a backend.
- Dependencies and inputs: `../overview.md`, `templates/plans/report.md`, `.agents/skills/html-communication/SKILL.md`. Read the overview before starting; its restrictions are binding.
- Scope: create only `docs/morrow-chat-redesign/index.html`, `option-a.html`, `option-b.html`, and `option-c.html`; write execution report at `.agents/plans/morrow-chat-redesign/reports/T01.md`. No product, dependency, README, existing mock, Supabase, or deployment edits. Primary owns publication and README.

## Execution steps

1. Inspect `git status --short` to record pre-existing changes. Read the HTML communication skill. Build every file with inline CSS/JS/SVG, no imports, network requests, fonts, images, frameworks, package additions, or generated art. All files must render both from a static HTTP server and when opened directly. Use the option filenames above and relative links so publishing the folder works.

2. Establish shared conventions across the proposals so differences are in composition, not missing features:
   - `lang="en"` for proposals, `lang="es"` for chooser; meaningful unique titles, viewport meta, semantic main/nav/header/form, real buttons and links.
   - Body background `#000`, white primary text, functional surfaces `#111`, borders `#262626`, secondary text `#A3A3A3`, focus/accent `#0A84FF`, solid primary buttons `#0066CC` with white text. System font for workspace, ui-monospace for onboarding. Workspace body text 14–15px, 1.5–1.6 line height; main titles about 22px. Use spacing and fine rules to organize; no decorative cards, pills, large avatar, gradients, shadows/glass, em dashes, gray subtitle lines above sections, or animated effects. Functional input/button corners 10–14px, not every container rounded.
   - Minimum usable touch targets 44px where practical; focus-visible outline 2px and offset 3px. Never remove focus rings. Icon-only controls have accessible names; SVG icon artwork is `aria-hidden`. Symbols supplement visible labels.
   - A thin external preview toolbar above the simulated application: `Static preview`, link `All options`, and a labeled native select `Preview view` with values `onboarding`, `chat`, `permission`, `review`. Its separation from product UI must be obvious. Keep it accessible and allow it to wrap at 390px. Below it, app uses remaining `100dvh` without browser horizontal scrolling. Provide a status region `role="status"` with short local-preview feedback.
   - Initial view defaults to `chat`. Support links such as `option-a.html?view=permission` by validating `URLSearchParams` against the four allowed values; invalid values fall back to chat. Selecting another view updates local state and the query string using `history.replaceState`, not navigation. Clear stale overlays/feedback and set the mission state appropriate to the chosen fixture.
   - Add stable hooks: `data-view="onboarding|chat|permission|review"` on view roots, hidden inactive views using the actual `hidden` attribute; `data-testid="chat-scroll"`, `composer`, `message-input`, `send-message`, `details-toggle`, `details-panel`, `mobile-menu`, `mobile-nav`, `permission-action`, `review-action`, `preview-feedback` where applicable. JS must not let CSS display rules override `[hidden]`. Every view must be present or rendered in a deterministic way accessible to browser verification.

3. Use these fixed fictional fixtures in each option. Keep actual visible copy concise; consistency enables fair visual comparison:
   - Companion `Morrow`, initial `M`; secondary selector entry `Scout`, initial `S`. User `Juanma`, initial `J`. General chat header `Morrow` with unobtrusive `General chat`. Left mission entries `Design the reading app` (In progress), `Research public references` (Permission needed), `Weekly design review` (Ready for review). A `New mission` control may open details or show `Preview only: mission creation is not connected.` It must not invent working backend behavior.
   - Populated conversation: user asks, `Help me shape a small reading app. I want one place to save articles and choose what to read next.` Morrow responds with a brief structured recommendation, `Start with an inbox and a reading queue. Keep saved links searchable. Which matters more today: capturing links quickly or choosing your next read?` User replies, `Choosing the next read. Keep it simple.` Morrow responds, `Then I would show three next reads, with the inbox one click away. We can turn that into a first screen.` Show user messages aligned right and Morrow left with at most subtle functional message backgrounds. Central content should feel like a useful ongoing conversation, not an empty hero.
   - Composer remains visually anchored at the bottom, with a labeled textarea (`Message Morrow`), concise placeholder, visible Send button, and optional `Shift + Enter for a new line` hint. Empty/whitespace send does nothing; Enter sends, Shift+Enter inserts newline. On send append a plainly labeled local user draft (`Preview message`) and report `Preview only: no message was sent.` Do not produce fake AI replies. Keep text escaped using textContent/DOM methods; do not interpolate user input into innerHTML. Chat scroll brings the local draft into view.
   - Permission view header shows `Research public references` and `Permission needed`. Chat says Morrow proposes reviewing three publicly available design references and asks before opening external sites. A functional action strip immediately above composer contains heading `Open public references?`, scope `Read 3 public pages. No sign-in, downloads, or account access.`, `Allow in preview`, and `Decline`. Make scope readable on mobile. Either choice shows `Preview only: permission choice recorded locally. No sites were opened.` Preserve fictional action context; no fetches, tabs, or real permission calls.
   - Review view header shows `Weekly design review` and `Ready for review`. Chat introduces a fictional draft and lists `Inbox`, `Next reads`, `Saved article view`. Above composer display a deliverable strip with `Reading app outline`, `Draft · 3 screens` (the middle dot is allowed), `View draft`, `Approve in preview`, and `Request changes`. `View draft` opens mission details containing the actual three-screen outline. Approval shows `Preview only: approval recorded locally.` Request changes exposes a labeled feedback textarea and confirm/cancel controls; nonempty confirmation shows `Preview only: revision request recorded locally.` Empty input remains open with visible validation; cancel restores the strip. Do not claim output was generated, published, or downloaded.
   - Details always has readable semantic sections `Goal`, `Progress`, `History`, `Output`. General context shows the reading-app goal, brief progress steps, a short fictional timeline, and empty-output copy. Permission details lists the scope above. Review details contains the three-screen outline: inbox saves and searches links; next reads offers three items with estimated reading time; saved article view shows original source and reading state. Label timelines/content as sample where needed.

4. Implement four-step onboarding in all proposals; visual difference is composition, not different requirements:
   - Sparse stationary stellar inline SVG, own geometry: tiny scattered points and one thin orbital curve. SVG is background only, pointer-events none, aria-hidden; no gradients, particle canvas, external art, blinking, typewriter, or auto-progress. Preserve #000 behind it and high text contrast.
   - Ui-monospace conversation with visible `Step 1 of 4` through `Step 4 of 4`, one prompt at a time: `What should I call you?`, `What are you working toward?`, `How would you like help?`, `What should we call your companion?`. Labeled text input and Continue button; final label `Enter chat`. Defaults/suggestions are `Juanma`, `Build a simple reading app`, `Plan and review`, `Morrow`; suggestions are text buttons that fill the answer rather than immediately advancing. Include `Research` and `Build` help alternatives.
   - Validate nonempty trimmed answers. Back preserves previously entered answers and allows edits. Final transition is local, updates current displayed user/companion names using safe DOM text, and selects chat. Toolbar can return to onboarding at the first step to compare. No storage/backend required. All forms have explicit labels; prompt, control, and chosen answer remain legible on mobile.
